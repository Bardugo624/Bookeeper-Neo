# Bookeeper 2.0 — Design

Data: 2026-11-20 · Stato: approvato

Le parole DEVE, NON DEVE, DOVREBBE, PUÒ seguono RFC 2119.
"Decisione utente" = scelta presa dal proprietario del progetto.
"Scelta di progetto" = scelta dell'autore del documento, correggibile.

---

## 1. Intento

Bookeeper 0.3 funziona, ma collegarlo e installarlo costa troppo. Il desktop
è Wails + Vue. Il server è Go dietro Caddy con mTLS, una CA per libreria e
Tailscale. Molte funzioni promesse non sono mai arrivate.

La 2.0 riscrive il prodotto con quattro obiettivi dichiarati dall'utente:

1. App desktop **Tauri + React**.
2. **Connessione e deployment semplici.**
3. **Beautification** senza cambiare stile né palette.
4. **Più funzionalità**, incluse quelle programmate e mai implementate.

## 2. Obiettivi, non-obiettivi, anti-obiettivi

### Obiettivi

- **G1 — Connessione.** Ogni percorso di primo avvio DEVE stare in una sola
  schermata. Aggiungere un dispositivo DEVE richiedere al più: indirizzo
  del server e un codice, oppure un QR.
- **G2 — Deployment.** Il server DEVE essere un solo binario, una sola
  porta, un solo volume dati. DEVE avviarsi senza file di configurazione.
  Caddy, Tailscale e il trust pool NON DEVONO più servire.
- **G3 — PC come host.** Una libreria locale DEVE poter essere condivisa in
  rete locale dall'app desktop con un interruttore.
- **G4 — Parità, poi novità.** La 2.0 DEVE coprire tutte le funzioni della
  0.3 prima di aggiungerne.
- **G5 — Identità visiva invariata.** Palette, tipografia, token e
  vocabolario componenti di `DESIGN.md` restano la fonte.
- **G6 — Schema nuovo.** Nessun dato né struttura dati della 0.x va
  conservato (decisione utente). Database e API si progettano da zero.

### Non-obiettivi (fuori dalla 2.0)

- Licenze Pro, gating, Bookeeper Cloud, migrazione locale→Cloud
  (decisione utente: progetto separato dopo la 2.0).
- App native negli store (decisione utente: mobile resta PWA).
- Telefono collegato a un PC di casa senza HTTPS valido (D7).
- Più librerie nella stessa installazione desktop (vedi §6.7).
- API pubblica con token, fonte SBN/OPAC, valore collezione, wishlist
  regalabile pubblica, pagina pubblica del prestito, consigli di lettura.
- Firma del codice Windows e notarizzazione macOS.
- Coda offline di modifiche sul mobile.
- Promemoria via email (richiede SMTP).
- Postgres o più processi server.

### Anti-obiettivi

- L'utente NON DEVE incontrare le parole certificato, CA, porta, tenant.
- La UI NON DEVE somigliare a un SaaS generico (vedi `PRODUCT.md`).
- Il codice React NON DEVE avere due percorsi distinti per libreria locale
  e remota.
- Nessuna funzione nuova entra prima che la parità sia verificata.

## 3. Vincoli

- SQLite resta l'unico database.
- **"0.3" in questo documento** = il codice al commit `c31c9ab`. Gli
  artefatti di versione dicono ancora 0.2.1. La lista di parità si
  riferisce a quel commit.
- Lingue: italiano e inglese, come oggi.
- Windows (WebView2) è la piattaforma primaria. macOS e Linux DOVREBBERO
  compilare in CI, senza firma.
- Un browser concede fotocamera, installazione e service worker solo su
  HTTPS con certificato riconosciuto. Conseguenza: D7 e §6.4.
- `PRODUCT.md` e `DESIGN.md` restano validi. Dove `DESIGN.md` cita PrimeVue
  va aggiornato, non contraddetto.

## 4. Approcci considerati

| | Approccio | Compromesso |
| --- | --- | --- |
| **A** | **Server per primo, a strati.** Core Rust a parità di API, poi desktop React a parità, poi mobile, poi funzioni a blocchi. | Connessione e deployment si chiudono subito. Il primo rilascio visibile arriva dopo due strati. |
| B | Fette verticali: un modulo alla volta da Rust a React. | Progresso visibile presto. Connessione e deployment instabili a lungo. |
| C | Riscrittura unica su ramo, un solo rilascio. | Massima libertà. Nessuna verifica intermedia. |

**Scelto: A** (decisione utente). Il focus dichiarato è connessione e
deployment: vanno chiusi e collaudati per primi. La parità con la 0.3 dà un
criterio oggettivo di "finito" prima delle novità.

Scartati a monte: Vue dentro Tauri (contraddice la richiesta); client prima
del server (obbliga a implementare mTLS in Rust per poi eliminarlo).

## 5. Decisioni dell'utente

| # | Decisione |
| --- | --- |
| D1 | Il server Go viene **riscritto in Rust** e vive dentro il core Tauri. |
| D2 | Autenticazione a **token dispositivo su HTTPS**. Niente mTLS. |
| D3 | Entrano tre blocchi: **Lettura e organizzazione**, **Scaffale fisico**, **Famiglia e mobile**. Più: palette comandi, storico prestiti, registro attività, filtri avanzati. |
| D4 | Monetizzazione fuori dalla 2.0. |
| D5 | Ordine di costruzione: approccio A. |
| D6 | Mobile resta **PWA**. |
| D7 | Il telefono si collega **solo a un server con HTTPS valido**. Col solo PC di casa non c'è mobile. Sostituisce la modalità ridotta valutata in precedenza. |
| D8 | **Nessuna compatibilità con la 0.x**: né dati, né schema, né forme dell'API. Niente migrazione. Non serve un database reale per le verifiche. |

## 6. Architettura

### 6.1 Struttura del repository

Scelta di progetto. La 0.3 resta dov'è (`server/`, `clients/`, `deploy/`),
congelata: solo correzioni critiche. La 2.0 nasce in alberi nuovi. Gli
alberi 0.3 vengono rimossi al rilascio della 2.0.0.

```
crates/
  bookeeper-core/      lib: database, dominio, API HTTP, auth, lookup,
                       copertine, etichette, import/export, backup
  bookeeper-server/    bin: server autonomo (config, TLS, mDNS, serve la PWA)
apps/
  desktop/             Tauri 2: src-tauri/ (guscio Rust + core) e src/ (React)
  mobile/              PWA React
packages/
  ui/                  token CSS + componenti React condivisi
  api/                 client tipizzato generato da OpenAPI + hook dati
  i18n/                messaggi it/en
docs/
  deploy.md            unica guida di installazione
```

### 6.2 Core Rust

- Un solo crate libreria usato da due eseguibili: app desktop e server.
- Un solo router HTTP, una sola porta. Sparisce la separazione
  "bootstrap" / "autenticato".
- Scelte di progetto: `axum` + `tokio`; `rusqlite` con SQLite incluso e
  FTS5; `argon2`; specifica OpenAPI generata dal codice.
- L'API è `/api/v1`, ridisegnata liberamente (D8). Le risorse della 0.3
  sono un riferimento funzionale, non un contratto. Non esistono più: CA,
  trust pool, recupero invito, CRL, superficie mobile separata.
- Codici d'errore: ogni errore utente DEVE avere un `error_code` stabile.
  Il client traduce. Chiude il punto rimandato della roadmap 1.3.
- **Database.** Schema nuovo, progettato per la 2.0 (D8). Parte già con
  stato di lettura, tag, stanze, ruoli, token dispositivo, copertine e
  campi copia. Niente colonne della CA. Lo schema 0.3 è un riferimento.
  Le migrazioni servono solo da 2.0 in avanti.
- **Multi-libreria.** Lo schema resta multi-tenant. Un server può ospitare
  più librerie indipendenti.

### 6.3 Copertine (scelta di progetto)

Oggi le copertine vivono solo nella cache del client. In 2.0 le conserva il
server.

- Alla creazione o al lookup di un libro il core scarica la copertina, la
  salva in `<dati>/covers/` e ne calcola il colore dominante.
- `GET /api/v1/books/{id}/cover` la serve. L'utente PUÒ caricarne una sua.
- Effetti: sparisce la cache IndexedDB del desktop; il dorso sullo scaffale
  usa il colore reale; il mobile ha le stesse copertine; il backup le include.

### 6.4 Connessione

#### Modello di autenticazione

- Un dispositivo abbinato possiede un **token di rinnovo** opaco, casuale,
  a rotazione. Il server ne conserva solo l'hash. Il riuso di un token già
  ruotato DEVE revocare il dispositivo.
- Le richieste portano un **token di accesso** JWT a vita breve (15 min),
  come oggi.
- Sul desktop i token vivono nel portachiavi del sistema operativo e non
  entrano mai nel codice React. Sul mobile vivono in IndexedDB.
- La revoca dispositivo resta. L'elenco dispositivi resta.
- La "password amministratore" della libreria sparisce. Le operazioni
  distruttive (ripristino, eliminazione libreria) chiedono di nuovo la
  password del proprietario.
- Login, abbinamento e setup DEVONO avere un limite di tentativi.

#### Percorsi di primo avvio

| Percorso | Cosa chiede | Cosa succede |
| --- | --- | --- |
| **Crea qui** | nome libreria, tuo nome | Il core parte dentro l'app. Nessuna password, nessun codice. |
| **Unisciti** | server (scelto da elenco o digitato) + codice, oppure email e password | Il dispositivo riceve i token. |
| **Crea su un server** | indirizzo, codice di setup, nome libreria, nome, email, password | Crea libreria e proprietario, abbina il dispositivo. |
| **Bentornato** | nulla, o password se la sessione è scaduta | Riprende la sessione. |

- **Codice di abbinamento**: 8 caratteri, monouso, 10 minuti. Lo genera un
  dispositivo già collegato (Impostazioni → Dispositivi → Aggiungi). Abbina
  un nuovo dispositivo alla stessa persona. È mostrato anche come QR: il QR
  apre la PWA e abbina il telefono senza digitare nulla.
- **Email e password su server con più librerie** (scelta di progetto): le
  email sono uniche solo per libreria. Il server verifica la password
  contro ogni utente con quella email. Una sola corrispondenza: entra.
  Più corrispondenze: l'utente sceglie tra quelle librerie, e solo quelle.
  Nessun elenco pubblico delle librerie.
- **Invito** (fase 6): come il codice di abbinamento, ma crea un nuovo
  membro con un ruolo. Chi lo riscatta sceglie nome, email e password.
  Fino alla fase 6 una libreria ha una sola persona, il proprietario, con
  più dispositivi: come nella 0.3.
- **Codice di setup**: il server lo stampa all'avvio finché non esiste
  alcuna libreria. In seguito lo si ottiene con `bookeeper-server
  setup-code`. Serve a creare una libreria. (Scelta di progetto.)
- **Scoperta in rete**: server e app in condivisione si annunciano via
  mDNS. Il percorso "Unisciti" elenca ciò che trova.
- **Password in locale**: "Crea qui" non la chiede. Diventa obbligatoria
  quando si attiva la condivisione in rete o si invita qualcuno.

#### Trasporto

- **Locale.** Il guscio Tauri inoltra le richieste al router del core in
  processo. Nessuna porta aperta.
- **Condivisione in rete (G3).** Interruttore in Impostazioni. L'app apre
  una porta in LAN con TLS a certificato autogenerato e si annuncia via
  mDNS. Serve solo altri computer con l'app desktop (D7).
- **Fiducia nel certificato autogenerato** (scelta di progetto). Otto
  caratteri non bastano a contenere un'impronta. Al primo contatto il
  desktop che si unisce e l'host mostrano la stessa frase di verifica,
  derivata dall'impronta. L'utente conferma che coincidono. Da lì
  l'impronta resta fissata. Vale per codice e per email e password.
- **Server autonomo.** Tre modalità TLS:
  - `off` — dietro un reverse proxy qualsiasi. Predefinita in Docker.
  - `acme` — certificato Let's Encrypt automatico dato un dominio.
  - `self` — autogenerato, per LAN, con impronta fissata come sopra.
    Solo client desktop.
- Il client desktop DEVE rifiutare indirizzi `http://` non locali.
- **Lato React.** `packages/api` espone un'interfaccia di trasporto con due
  implementazioni: comando Tauri (desktop) e `fetch` (mobile). Tutto il
  resto del codice è identico.

#### Mobile e HTTPS (D7)

| Server | Telefono |
| --- | --- |
| Dominio con HTTPS valido (`acme`, o `off` dietro un proxy HTTPS) | PWA completa: scanner, installazione, offline. |
| PC di casa in condivisione, server `self`, server `off` senza proxy | Nessun accesso da telefono. |

- La PWA aperta fuori da un contesto sicuro DEVE mostrare solo una pagina
  che spiega cosa serve, senza parole tecniche.
- L'app desktop DEVE mostrare "Aggiungi telefono" solo quando il server ha
  HTTPS valido. Altrimenti spiega cosa manca e rimanda alla guida.
- `docs/deploy.md` DEVE includere una ricetta per esporre un server di casa
  con un tunnel di terze parti, per chi vuole il telefono senza dominio
  proprio.

### 6.5 Deployment

- `bookeeper-server`: binario statico per Linux amd64/arm64, Windows,
  macOS. Contiene PWA e migrazioni.
- Avvio senza configurazione: crea la cartella dati, stampa indirizzo e
  codice di setup.
- Configurazione opzionale, per variabili o flag: cartella dati, porta,
  modalità TLS, dominio, indirizzo pubblico, mDNS.
- Immagine Docker multi-architettura pubblicata dalla CI a ogni tag.
  `docker-compose.yml`: un servizio, un volume, una porta.
- Aggiornare il server = scaricare la nuova immagine e riavviare.
- **Backup nel core.** Backup programmato con rotazione in
  `<dati>/backups`, sia in app sia su server. Formato: archivio con dati
  della libreria e copertine.
- **Rilasci.** Un workflow su tag produce: binari server, immagine Docker,
  installer desktop, manifest di aggiornamento.
- **Aggiornamenti desktop.** Updater di Tauri con firma degli aggiornamenti.
  Canali stable e beta.
- **Rimossi**: Caddyfile, servizio Tailscale, trust pool, `bootstrap.sh`,
  `preflight.sh`, `gen-serve-config.sh`, `deploy.ps1`, le quattro guide
  `SETUP.md`. Li sostituisce `docs/deploy.md` con tre ricette: PC di casa,
  NAS o Raspberry con Docker, VPS con dominio.

### 6.6 Rapporto con la 0.x

Nessuna migrazione (D8). La 2.0 è un'installazione nuova. Chi vuole
portare un catalogo usa l'import (Goodreads, Calibre, LibraryThing, CSV).
Il server di produzione viene reinstallato da zero. L'updater della 0.3
non deve portare alla 2.0.

### 6.7 Desktop: Tauri + React

Scelte di progetto, tranne dove indicato.

- Tauri 2, React, TypeScript, Vite.
- Stato server con una libreria di query e cache; stato UI in uno store
  leggero; router con rotte per modulo.
- Struttura a moduli come oggi: `books`, `shelves`, `loans`, `wishlist`,
  `stats`, `devices`, `settings`, più `reading`, `family`, `audit`.
- Le regole di `FRONTEND_MODULES_PLAN.md` restano: componenti sotto 250
  righe, logica in hook, nessuna chiamata di rete dai componenti.
- Guscio Rust: trasporto API, portachiavi, core in processo, condivisione
  in rete, updater, dialog file, notifiche, istanza singola, link
  `bookeeper://` per l'abbinamento.
- Le cinque viste segnaposto morte in `views/` non vengono portate.
- **Una libreria per installazione** (scelta di progetto), come nella 0.3.
  Token, impostazioni e dati locali DEVONO però essere salvati sotto un
  identificativo di connessione, così un futuro selettore di librerie non
  richiede di spostare dati.

### 6.8 Sistema visivo e beautification

**Resta identico** (decisione utente): verde salvia `#4d8369`, neutri
caldi, Inter + Lora, token `--bk-*`, durate ed easing, colori scaffale,
tinte tela delle copertine, anti-pattern vietati.

**Cambia la base tecnica.** PrimeVue esce. `packages/ui` contiene:

- i token `--bk-*` copiati da `tokens.css`, più le scale primaria e
  neutra oggi definite nel preset PrimeVue;
- componenti propri su primitive accessibili senza stile: bottone, campo,
  select, dialog, drawer, menu, tab, toast, tooltip, tag, tabella, stato
  vuoto, scheletro;
- `BookCover`, `ShelfSvg`, `StatCard`, barre di riempimento, portati
  fedelmente.

**Beautification proposta** (scelta di progetto, da confermare sui mockup):

1. Barra del titolo integrata nella sidebar, senza cornice di sistema.
2. Scheletri di caricamento in ogni vista.
3. Transizione condivisa copertina: dalla griglia al dettaglio.
4. Scheda libro con impaginazione editoriale.
5. Scaffali: dorsi col colore reale, larghezza dal numero di pagine,
   feedback di trascinamento.
6. Griglie e tabelle virtualizzate per cataloghi grandi.
7. Icone coerenti, un solo set a tratto. Sostituisce PrimeIcons.
8. Revisione di spaziature, densità e parità del tema scuro.
9. Stati vuoto, errore e offline disegnati per ogni vista.

**Cancello visivo.** Prima di portare le viste, la fase 2 DEVE produrre
mockup di quattro schermate: primo avvio, Libri, Scaffali, scheda libro.
L'utente li approva. L'aspetto è una sua decisione.

### 6.9 Mobile PWA

- Riscritta in React. Usa `packages/ui`, `packages/api`, `packages/i18n`.
- Servita dal core sulla stessa origine dell'API.
- Abbinamento: QR o codice. Niente più CSR né certificati nel browser.
- Funziona solo su server con HTTPS valido (D7).
- Aggiornamento: banner non bloccante, come oggi.

## 7. Funzioni

### 7.1 Parità con la 0.3 (obbligatoria)

Libri (CRUD, ricerca full-text, griglia e tabella, lookup ISBN da Google
Books, Open Library e Anna's Archive, numero progressivo, eliminazione
multipla) · Scaffali SVG (configurazione, assegnazione, riempimento) ·
Prestiti · Wishlist con conversione in libro · Statistiche · Dispositivi e
abbinamento · Import Goodreads/Calibre/LibraryThing · Export JSON/CSV ·
Backup e ripristino · Etichette PDF · i18n it/en · Onboarding del primo
libro · Aggiornamenti con note di versione · Tema chiaro/scuro/sistema ·
Mobile: cerca, scansiona, account.

### 7.2 Inclusi comunque (D3)

- **Palette comandi** (`Ctrl+K`): naviga, cerca libri, lancia azioni,
  "Dov'è?". Scorciatoie da tastiera documentate.
- **Storico prestiti**: vista dei prestiti chiusi; suggerimento dei nomi
  già usati.
- **Registro attività**: vista di `audit_log` in Impostazioni, con filtri
  per persona, dispositivo, azione. Solo proprietario e admin.
- **Filtri avanzati** nei Libri: stato lettura, tag, stanza, scaffale,
  genere, lingua, anno, formato, in prestito. Ordinamenti.
- **Campi copia**: condizione, data di acquisto, prezzo. Colonne già
  presenti, mai esposte.

### 7.3 Blocco L — Lettura e organizzazione

- **Stato di lettura** per persona e per libro: da leggere, in lettura,
  letto, abbandonato; date; valutazione privata; nota. Usa `reading_log`
  con una colonna di stato in più.
- **Tag**: creazione, colore dalla palette scaffali, assegnazione, filtro.
  Usa `tags` e `book_tags`.
- **Stanze**: uno scaffale appartiene a una stanza. La dashboard scaffali
  si raggruppa per stanza. Usa `libraries`; `shelves` riceve il
  riferimento. La stanza di un libro è quella del suo scaffale.
- **Statistiche di lettura**: letti per anno, pagine, calendario di
  lettura, generi letti.
- **"Il tuo anno in libri"**: immagine generata sul client, salvabile.

### 7.4 Blocco S — Scaffale fisico

- **"Dov'è?"**: da ricerca, palette o scheda libro si apre lo scaffale. Il
  dorso si sfila e pulsa. Testo: "Narrativa · mensola 3 · posto 12".
  Anche su mobile.
- **Drag & drop**: riordina in uno scaffale, sposta tra scaffali, trascina
  dal vassoio dei non collocati. DEVE esistere un'alternativa da tastiera.
  Il server valida le posizioni in una transazione.
- **Dorso dal colore reale**: dal colore dominante della copertina.
  Ripiego: tinta deterministica attuale.
- **Larghezza dorso**: derivata dal numero di pagine, modificabile.
- **Scan-a-scaffale** (mobile): scegli scaffale e mensola,
  scansiona in sequenza. Libro noto: collocato nel posto successivo. Libro
  nuovo: lookup, creazione, collocazione. Annulla ultimo. Riepilogo finale.

### 7.5 Blocco F — Famiglia e mobile

- **Più persone**: ruoli proprietario, admin, membro, ospite (già nello
  schema). Inviti con ruolo. Vista di gestione persone. Il controllo dei
  permessi per ruolo nasce nel core già in fase 1; inviti, gestione
  persone e relative API arrivano qui.

  | Ruolo | Può |
  | --- | --- |
  | ospite | leggere |
  | membro | + libri, scaffali, prestiti, propria wishlist, proprie letture |
  | admin | + persone, dispositivi, import, backup, registro attività |
  | proprietario | + ripristino, eliminazione libreria, cambio proprietario |

- **"Di chi è"**: proprietario opzionale del libro. **"Chi lo legge"**:
  deriva dallo stato di lettura.
- **Wishlist di famiglia**: ognuno ha la sua; i membri vedono le altre.
- **Prestiti a membri**: chi prende in prestito può essere un membro.
- **Mobile esteso**: scheda libro modificabile nei campi base, prestiti
  (crea, restituisci), wishlist (aggiunta rapida, conversione), stato di
  lettura, scaffali in sola lettura con "Dov'è?".
- **Anti-doppio-acquisto** (mobile): indice locale ISBN → titolo e
  posizione, sincronizzato in IndexedDB. Risposta offline in meno di un
  secondo dopo la scansione.
- **Promemoria prestiti**: badge in sidebar e notifica di sistema sul
  desktop per i prestiti scaduti. Notifiche push sulla PWA.
  Le push sono l'ultima voce del blocco e PUÒ slittare a una 2.1.

## 8. Fasi

Ogni fase ha un proprio piano di implementazione, scritto quando la fase
precedente è chiusa. Una fase chiude solo col proprio criterio d'uscita.

| Fase | Contenuto | Criterio d'uscita |
| --- | --- | --- |
| **0 — Fondamenta** | Workspace Rust e JS, CI, scheletro di core, server, desktop e PWA che compilano; schema del database; specifica OpenAPI generata dal core. | La CI compila e testa tutto. Un endpoint di salute risponde da server e da app. |
| **1 — Core e deployment** | Core Rust con tutte le risorse della 0.3; nuovo modello auth e abbinamento; controllo permessi per ruolo; copertine lato server; backup nel core; `bookeeper-server`; TLS `off`/`acme`/`self`; mDNS; Docker. | Test di integrazione verdi per ogni risorsa. Da `docker run` a libreria creata e dispositivo abbinato senza file di configurazione. |
| **2 — Desktop a parità** | Mockup e cancello visivo; `packages/ui`; guscio Tauri; percorsi di primo avvio; tutti i moduli 0.3; impostazioni; updater; condivisione in rete. | Lista di parità §7.1 spuntata. Rilascio `2.0.0-beta.1` sul canale beta: un proprietario, più dispositivi. |
| **3 — Mobile a parità** | PWA React: abbinamento QR/codice, cerca, scansiona, account, pagina "serve HTTPS". | Parità con la PWA 0.3. Abbinamento da QR senza digitare, su server con HTTPS valido. |
| **4 — Inclusi comunque + Blocco L** | §7.2 e §7.3. | Funzioni verificate su desktop e mobile. |
| **5 — Blocco S** | §7.4. | Come sopra. |
| **6 — Blocco F** | §7.5. | Come sopra. |
| **7 — Rilascio** | Verifica accessibilità, prestazioni con 10.000 libri, `docs/deploy.md`, reinstallazione del server di produzione, rimozione alberi 0.3, aggiornamento `DESIGN.md`, `README`, `ROADMAP`. | Rilascio `2.0.0` stable. |

Dimensione relativa: la fase 1 e la fase 2 sono le più grandi. Insieme
valgono circa metà del lavoro.

## 9. Verifica

- **Parità.** È funzionale, non di protocollo: la lista §7.1 spuntata
  voce per voce contro la 0.3 in esecuzione.
- **Core.** Test di integrazione per risorsa su SQLite temporaneo. Test
  dedicati per: rotazione e riuso dei token, permessi per ruolo, validazione delle posizioni sugli scaffali.
- **Interfaccia.** Test di componenti e hook. Test end-to-end nel browser
  contro un `bookeeper-server` reale, possibili perché la UI è indipendente
  dal trasporto.
- **Accessibilità.** Contrasto, tastiera, `prefers-reduced-motion`, come da
  `PRODUCT.md`.

## 10. Lasciato a chi implementa

- Librerie specifiche per: query e cache, store, router, primitive UI,
  icone, grafici, drag & drop, tabella, scansione barcode, PDF, DataMatrix,
  mDNS, ACME, portachiavi.
- Forma esatta delle nuove risorse API, entro le convenzioni esistenti.
- Formato dell'archivio di backup.
- Algoritmo del colore dominante e soglie pagine → larghezza dorso.
- Porta predefinita e nomi delle variabili di configurazione.
- Conversione dei file di messaggi da vue-i18n al formato scelto.
